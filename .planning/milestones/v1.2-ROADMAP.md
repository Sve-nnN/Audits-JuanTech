# Milestone v1.2: Detección de renderizado + exportación de reportes

**Status:** ✅ SHIPPED 2026-07-08
**Phases:** 11-15
**Total Plans:** 15 (4 + 3 + 4 + 1 + 3)

## Overview

Con el pipeline funcional (v1.0) y la UI de marca (v1.1) ya validados, v1.2 amplió el producto de forma estrictamente aditiva, sin romper el pipeline de crawl/checks/scoring/diff/email. La secuencia siguió un orden de riesgo ascendente definido por el research: primero checks Cheerio puros sobre HTML ya almacenado (canonicals profundos + jerarquía de encabezados + fix de dato CWV), cero infraestructura nueva; luego la única pieza que toca worker + Docker, el pase selectivo de render CSR/SSR con Playwright sobre una muestra, en aislamiento y con degradación limpia; después la fundación de export (lecturas puras de datos ya persistidos con librerías JS puras, sin Chromium en Vercel) que genera PDF con branding, Markdown-para-LLM y PPTX desde una route Node; el botón de export como UI fina sobre esa route; y por último la UX del reporte (categoría REPORT nueva, fuera del sketch original de research): agrupación de issues por tipo en dropdowns e indicador de estado JSON-LD por página. El resultado: la auditoría ahora detecta más errores, dice si una página es SSR o CSR, y el reporte se exporta en tres formatos desde un control accesible.

**Depends on**: Phase 6 (motor de checks + scoring + diff de v1.0)

- [x] 11-02: headingsCheck (ONPAGE-08): saltos de nivel, vacíos, fuera de orden, H1 duplica title (HEAD-01..03)
- [x] 11-03: Fix REPORT-03 — `source` en PerfIssueDraft + mapPerfIssues + mapeo del worker
- [x] 11-04: Guardarraíl SC#5 — no-colapso de fingerprints + estabilidad de score de fixture

**Details:**

### Phase 12: Detección de renderizado CSR/SSR

**Goal**: La auditoría determina, sobre una muestra representativa, si cada página se renderiza server-side o client-side comparando HTML crudo vs DOM renderizado, y lo reporta como riesgo sin comprometer la estabilidad del pipeline ni la frontera web/worker.
**Depends on**: Phase 11 (fingerprints sub-tipados y scoring ya endurecidos) — comparte el motor de checks de v1.0
**Requirements**: RENDER-01, RENDER-02, RENDER-03
**Plans**: 3 plans

Plans:

- [x] 12-01: paquete @auditor/render + lógica pura de detección SSR/CSR (RENDER-01/02)
- [x] 12-02: cliente Playwright (pool, timeout, cleanup en finally, concurrencia 2) + runRenderSample con degradación (RENDER-01/03)
- [x] 12-03: integración en worker + Dockerfile pinneado + aserción Playwright fuera del bundle web (RENDER-01/03, SC#4)

**Details:**
Nuevo paquete worker-only `@auditor/render` (cheerio, cero Playwright en la capa de decisión): `detectRenderVerdict` compara el `Page.html` crudo vs el `RenderedSnapshot` (title / H1 / texto, ratio < 0.60 → CSR), severidad SSR→ok / CSR→warning (NUNCA critical), categoría "aeo", fingerprint `RENDER-01:<verdict>:<url>`; `RENDER_CSR_RATIO=0.60` tuneable. La capa Playwright (`launchBrowser` 1 Chromium con args low-shm + `snapshotPage` con contexto fresco, timeout 15s vía Promise.race, `context.close()` en finally en TODOS los caminos) corre en `runRenderSample`, best-effort, reusando `selectSample` (`MAX_RENDER_PAGES=10`, independiente de PSI), `lanes = RENDER_CONCURRENCY(2)`, degradando cualquier throw/block/timeout a `undeterminedVerdict` sin rechazar nunca (RENDER-03). Cableado en el worker tras el pase PSI con doble guarda (degradación interna + try/catch externo → la auditoría siempre llega a `done`); sus issues `aeo` entran a `issueRowsWithoutDiff` sin tocar diff/score/persist. Primer `apps/worker/Dockerfile` multi-stage pinneado a `mcr.microsoft.com/playwright:v1.61.1-noble` (SC#4). Guardarrail `scripts/assert-no-playwright-in-web.mjs` (`assert:web-boundary`) prueba que `@auditor/render` nunca resuelve en el grafo de `apps/web`. Verificación: passed 4/4 en código; verificación humana de runtime Docker diferida y aceptada (ver Deferidos).

### Phase 13: Fundación de export + serializers

**Goal**: El reporte puede generarse on-demand en tres formatos (PDF con branding, Markdown-para-LLM y PPTX) desde una route Node de Next.js, leyendo datos ya persistidos con librerías JS puras — sin Chromium en el bundle web.
**Depends on**: Phase 12 (los reportes exportados ya incluyen los hallazgos CSR/SSR); consume el modelo de datos del reporte de v1.0
**Requirements**: EXPORT-01, EXPORT-02, EXPORT-03, EXPORT-05
**Plans**: 4 plans

Plans:

- [x] 13-01: Paquete @auditor/report-model (buildReportModel) + refactor de page.tsx a single source of truth
- [x] 13-02: Paquete @auditor/export — cap top-N compartido + serializers Markdown-LLM y PPTX
- [x] 13-03: Serializer PDF con @react-pdf/renderer + fuente de marca embebida (acentos/ñ)
- [x] 13-04: Route Node GET /api/audits/[id]/export (3 formatos) + guardarrail de frontera Chromium

**Details:**
Nuevo paquete puro `@auditor/report-model`: `buildReportModel(auditId)` devuelve un `ReportModel` serializable (cero React/Prisma/PII) que reemplaza el ensamblado inline de `page.tsx` (single source of truth compartida por report UI + serializers de export + grouping); expone `priorityCandidates` (set completo critical+warning, fuente de la M en "N de M") aparte de `priorityIssues` (cap 60); retorna `null` para audit inexistente o `status != done`. Paquete puro `@auditor/export` (JS puro, sin Chromium): `priority.ts` con `EXPORT_TOP_N=50` y `prioritizeIssues()` operando siempre sobre `priorityCandidates` (única fuente del cap, nota "Mostrando N de M"); `markdown.ts` estructurado por issue → checkId → página/selector → valor medido → criterio → recomendación (listo para LLM); `pptx.ts` vía pptxgenjs con fórmula `BASE_SLIDES=7` + 0..`MAX_ISSUE_SLIDES(5)` → total garantizado en [7,12]. Serializer PDF `toPdf` vía `@react-pdf/renderer` (renderer propio, sin navegador headless) con roles tipográficos v1.1 embebidos por `Font.register`: Khand (400/600) en TODOS los headings + Geist Sans (400) en body (Array NO se embebe); TTFs vendorizadas reproduciblemente con cobertura Latin completa (áéíóúñ¿¡). Route Node `GET /api/audits/[id]/export?format=pdf|md|pptx` (runtime nodejs) que lee `buildReportModel` y devuelve el archivo con `Content-Type`/`Content-Disposition` por formato, validación con type guard (→400) y 404 si el modelo es null; acceso por auditId sin auth (free tier), cero PII. Guardarrail de frontera extendido (Check D) para probar que `@auditor/export`, ya dep real del web, no arrastra browser engine. Verificación: passed 4/4 en código; verificación humana del render visual del PDF diferida y aceptada (ver Deferidos).

### Phase 15: UX del reporte — agrupación e indicadores

**Goal**: El reporte presenta los issues agrupados por tipo en dropdowns y muestra el estado del JSON-LD por página, para que la información sea legible sin saturación. Categoría REPORT nueva, adicional al sketch de research.
**Depends on**: Phase 10 (pantallas de reporte y de páginas + grafo de v1.1) y Phase 11 (los nuevos issues de canonical/headings ya se agrupan bien)
**Requirements**: REPORT-01, REPORT-02, REPORT-04
**Plans**: 3 plans
**UI hint**: yes

Plans:

- [x] 15-01: Helpers puros en @auditor/report-model — groupIssuesByType (orden severidad→cantidad) + jsonLdStateForPage (4 estados)
- [x] 15-02: Componente IssueTypeGroup + cableado en "Issues prioritarios" y "Detalle por categoría" (REPORT-01/02)
- [x] 15-03: Badge JSON-LD de 4 estados por página en la lista de páginas (REPORT-04)

**Details:**
Dos helpers puros en `@auditor/report-model` (sin React/Prisma): `groupIssuesByType(issues)` — única fuente del orden — agrupa por clave compuesta `checkId`+`title` (sub-tipos del mismo checkId con títulos distintos = grupos separados), severidad del grupo = la peor, ordena por (peso de severidad asc, count desc) con empate resuelto por orden de inserción del Map (estable), sin mutar la entrada ni perder issues; y `jsonLdStateForPage(schemaSeverities, hasSchemaGraph)` = peor de 4 estados con precedencia critical→"error" > warning→"warning" > (grafo presente)→"ok" > "absent". Componente `IssueTypeGroup` cableado en "Issues prioritarios" y en "Detalle por categoría" (problemas y correctos), agrupando por tipo en dropdowns con orden consistente. `JsonLdBadge` (client component) mapea los 4 estados a variantes existentes de `Badge` sin colores nuevos (error→critical, warning→warning, ok→"{n} entidad(es)", absent→neutral "Sin JSON-LD"); `pages/page.tsx` añade una segunda consulta `issue.findMany({ where:{ auditId, category:"schema" } })` agrupada por pageId y renderiza el peor estado por página, resto de la fila intacto. ## Milestone Summary

**Decimal Phases:** Ninguna (sin inserciones urgentes durante v1.2).

**Key Decisions:**

- Aditivo sobre v1.0/v1.1 — cero cambios que rompan el pipeline validado; los issues nuevos entran por los paths de persistencia/diff/scoring existentes.
- Secuencia de riesgo ascendente: checks puros → render (única pieza worker+Docker) → export (libs JS puras) → UI. Aisla la infraestructura nueva a una sola fase.
- Render CSR/SSR como riesgo informativo (severidad ok/warning), NUNCA falla dura del score — evita penalizar SSR con hidratación parcial.
- Solo se renderiza una muestra representativa (reusa `selectSample`, `MAX_RENDER_PAGES=10`), nunca las 500 URLs — 5–10× costo/tiempo evitado.
- Chromium fuera del bundle de Vercel: exports vía librerías JS puras (`@react-pdf/renderer`, pptxgenjs), garantizado por el guardarrail `assert:web-boundary` (Checks C/D).
- `buildReportModel` como single source of truth para report UI + serializers de export + grouping, evitando ensamblado divergente de datos.
- PDF con roles tipográficos de marca embebidos (Khand headings + Geist Sans body); Array reservada a display, no se embebe.
- Exports on-demand en route Node (sin cola/async) — son lecturas rápidas de datos ya persistidos.
- `groupIssuesByType` con orden estable por inserción del Map (sin depender de la estabilidad de Array.sort).

**Issues Resolved:**

- Issues de Rendimiento/CWV mostraban "—" en vez de la URL analizada (REPORT-03) → `source` propagado en todas las ramas de `mapPerfIssues`.
- Múltiples hallazgos por página (canonical + headings) podían colapsar en el diff → fingerprints sub-tipados (`TECH-04:chain`, `ONPAGE-08:skip`) garantizan una fila por sub-tipo.
- Frontera web/worker verificada programáticamente: Playwright/Chromium nunca entra al bundle de Vercel (guardarrail `assert:web-boundary`).
- Presión de disco (ENOSPC) durante la ejecución → se liberaron cachés `.next`/`.turbo`; builds quedaron verdes.

**Issues Deferred:**

- **Verificación humana runtime Docker (Phase 12)** — correr el contenedor pinneado con una auditoría real (≥10 páginas) en paralelo con PSI para confirmar cero Chromium huérfanos / OOM bajo concurrencia 2. Verificado por test unitario + contrato de código; el comportamiento real de memoria solo se observa ejecutando el contenedor. Naturalmente parte de la fase de deploy.
- **Verificación humana render visual del PDF (Phase 13)** — abrir un PDF real para confirmar visualmente que los glifos Khand/Geist y los acentos áéíóúñ¿¡ se renderizan bien. La extracción de texto lo confirma programáticamente; la apariencia del branding solo se cierra abriendo el archivo.

Ambos ítems fueron aceptados por Juan como diferidos al deploy y no bloquean el cierre. Ver STATE.md `## Deferred Items`.

**Technical Debt Incurred:**

- Fragilidad latente (integration WARNING, no blocker): `groupIssuesByType` agrupa por checkId+title; la separación de sub-tipos que comparten checkId (TECH-04, ONPAGE-08) depende de que los títulos nunca colisionen. Hoy no colisionan; un título futuro duplicado mezclaría sub-tipos silenciosamente.
- Fragilidad latente (integration WARNING, no blocker): el estado JSON-LD por página (REPORT-04) arma su propio query Prisma en `pages/page.tsx`, en paralelo a `buildReportModel` (que no transporta estado por página). Segunda ruta de ensamblado de datos schema que podría divergir si cambian los criterios de severidad.
- Sin deuda bloqueante. Candidatos a endurecer en v2 o al tocar esas áreas.
